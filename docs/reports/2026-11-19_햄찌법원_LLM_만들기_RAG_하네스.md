# 햄찌법원만의 LLM 만들기 — API만 쓰는 구조에서 RAG·미세조정·하네스를 어떻게 하는가

> 작성일: 2026-11-19 · 사용자 요청 보고서 (DEC-042)
> 읽는 사람: 서비스 운영자. 코드 위치는 저장소 기준입니다.
> 확인한 것과 추정을 구분해 적었습니다. 미세조정 제공 여부는 웹 검색으로 확인했고 출처가 대부분 제3자 글이라 9절에 한계를 적었습니다.

---

## 0. 한눈에

- **맞습니다. API는 매 요청이 새 컨텍스트입니다.** 모델은 이전 요청을 기억하지 않고, 그 요청에 담아 보낸 글만 봅니다.
- 그래서 "햄찌법원만의 LLM"은 모델 가중치를 바꿔서 만드는 것이 아니라, **요청마다 무엇을 담아 보내고 나온 답을 어떻게 거르는지**(하네스)로 만듭니다. 모델은 빌려 쓰고, 지식·규칙·예시·검증은 우리가 가집니다.
- **미세조정은 지금 Claude에서 쓸 수 없습니다.** 대신 같은 효과를 내는 방법이 있습니다: 우리 데이터로 만든 **라벨 예시를 질문마다 골라 넣는 것**(동적 예시)입니다. 미세조정이 "가중치에 예시를 새기는 것"이라면 이것은 "매번 관련 예시를 보여 주는 것"입니다.
- 이미 갖춘 것: 법제처 실시간 검색(RAG), 인용 검증, 비용 상한, 절차 라벨, 예시 답변 33건. **이번에 더하는 것**: 공개 질문 수집 → Haiku 라벨링(복수 라벨·온/오프라인·새 라벨 제안) → 예시 뱅크 → 질문 해석에 동적 예시 + 복수 라벨.

## 1. 원리 — API는 무엇을 기억하는가

| | 로컬 LLM | Claude API (지금 구조) |
|---|---|---|
| 모델 가중치 | 내 것. 미세조정으로 바꿀 수 있음 | Anthropic 것. 바꿀 수 없음 |
| 요청 사이의 기억 | 없음 (같음) | 없음 — 요청마다 처음부터 |
| 지식을 넣는 법 | 미세조정 또는 RAG | **RAG와 지시문뿐** |
| 말투·형식을 맞추는 법 | 미세조정 | 지시문 + 예시 + 출력 형식 강제(구조화 출력) |
| 비용 구조 | 장비·운영 | 토큰당 과금 — 넣는 글이 곧 비용 |

핵심은 한 줄입니다: **모델이 아는 것 = 학습된 일반 지식 + 이번 요청에 넣은 글.** 햄찌법원이 "법령을 지어내지 않는" 이유도 모델이 똑똑해서가 아니라, 그 요청에서 법제처로부터 가져온 조문·판례만 근거로 쓰게 하고 나온 인용을 다시 대조하기 때문입니다(절대 규칙 1).

"이전 텍스트만 참조"하는 것은 약점이자 장점입니다. 모델이 몰래 바뀌지 않으므로, 넣은 글과 나온 글을 모두 우리가 통제하고 기록할 수 있습니다.

## 2. 햄찌법원 LLM의 구성 — 모델 + 다섯 겹의 하네스

```
사용자 질문 (가린 문장)
   │
   ▼
① 질문 해석 ── Haiku 1회 ─────────────────────────────┐
   · 절차 라벨(복수) · 온/오프라인 · 검색어 · 새 라벨 제안   │  ← [예시 뱅크]에서 비슷한 질문 3~5개를
   │                                                    │     골라 지시문에 붙인다 (동적 예시)
   ▼                                                    │
② 검색 (RAG, 법제처 무료) ◄── 라벨의 기본 조문·판례 검색어 ┘
   · 자연어 법령 검색 + 카테고리 기본 조문 + 판례 검색·상세
   │
   ▼
③ 답변 ── 사용자가 고른 모델 1회 (Haiku / Sonnet / Opus)
   · 근거 목록 안에서만 · 출처 키와 원문 구절을 붙여서 (구조화 출력)
   │
   ▼
④ 검증 (모델 없음)
   · 원문 구절 대조 · 법제처 재조회 · 숫자·단정 표현·개인정보 거르기
   │
   ▼
⑤ 화면 · 저장 · 되먹임
   · 절차 타임라인 · 사건 구조도 · 새 라벨 제안은 승인 대기 · 평가셋 회귀
```

| 겹 | 로컬 LLM이라면 | 햄찌법원에서의 구현 | 코드 |
|---|---|---|---|
| ① 지시문 | 시스템 프롬프트 | 고정 지시문(프롬프트 캐시 대상) + 라벨 목록 | `lib/ai/prompts.ts`, `lib/procedure/sections.ts` |
| ② 지식 (RAG) | 벡터 DB 검색 | 법제처 실시간 검색 + 카테고리 기본 조문 78개 + 쟁점별 검색 | `lib/demo/free.ts`, `lib/search/law-source.ts`, `lib/procedure/categories.ts` |
| ③ 예시 (미세조정 대체) | 미세조정 데이터 | **라벨 예시 뱅크** — 질문과 비슷한 예시를 골라 넣음 | `lib/ai/label-bank.ts` (이번에 추가) |
| ④ 출력 계약·검증 | 후처리 | 구조화 출력(JSON 형식 강제) + 인용 검증 + 문구 거르기 | `lib/ai/policy.ts`, `lib/citations/` |
| ⑤ 운영 | 서빙 | 질문 1건 비용 상한, 기간 예산, 실패 시 한 단계 낮은 방식으로 내려가기 | `lib/ai/client.ts`, `lib/ai/cost.ts`, `lib/auth/rate-limit.ts` |

## 3. RAG — 무엇을, 어떻게 찾아 넣는가

RAG는 "질문과 관련된 자료를 찾아 요청에 붙이는 것"입니다. 벡터 검색은 그 방법 가운데 하나일 뿐입니다.

| 찾아 넣는 것 | 지금 방식 | 왜 이 방식인가 |
|---|---|---|
| 법령 조문 | 법제처 지능형 법령검색(자연어) + 카테고리 기본 조문 | 조문은 항상 **현행**이어야 해서 저장해 두지 않고 요청 때 가져온다 (DEC-007·009) |
| 판례 | 법제처 판례 검색(법률 용어 검색어) + 상세 조회 | 같음. 판례 본문은 저장하지 않는다 |
| 절차 타임라인 | 규칙 → 질문 해석 라벨 → 저장된 라벨 | 문구에 숫자·단정 표현이 들어가면 안 돼 고정 문안을 쓴다 |
| **질문 해석 예시** | **예시 뱅크에서 낱말 겹침으로 고른다** (이번에 추가) | 라벨 30개에 예시 수백 개 규모라 벡터 없이도 충분하다 |

**임베딩(벡터 검색)을 지금 안 쓰는 이유**
- Anthropic은 임베딩 모델을 제공하지 않습니다(공식 문서가 Voyage AI 같은 외부 제공자를 안내). 쓰려면 별도 계약·키·비용이 필요하고, 가린 문장이라도 사용자 질문을 **또 다른 회사에 보내게** 됩니다(개인정보 처리방침 변경 대상).
- 지금 규모에서는 필요가 없습니다. 법령·판례는 법제처 검색이 이미 해 주고, 예시 뱅크는 수백 건이라 낱말 겹침으로 충분합니다.
- 필요해지는 시점: 예시 뱅크가 수천 건을 넘거나, 수집한 판례를 자체 DB에 넣어 의미 검색을 하게 될 때. 스택에 pgvector가 이미 있어(DEC-004) 그때 붙이면 됩니다.

## 4. 미세조정 — 지금 할 수 있는가, 대신 무엇을 하는가

**확인한 사실 (2026-11 기준, 9절 한계 참고)**
- Anthropic API는 미세조정을 제공하지 않습니다.
- 예전에 Amazon Bedrock에서 Claude 3 Haiku 미세조정이 있었지만, 그 모델이 지원 종료되면서 지금 쓸 수 있는 Claude 모델에는 미세조정 경로가 없는 것으로 보입니다.

**대신 하는 것 — 효과가 같은 순서대로**

| 미세조정으로 얻으려던 것 | 대체 방법 | 햄찌법원 적용 |
|---|---|---|
| 우리 분류 체계를 따르게 | 라벨 목록 + **비슷한 질문의 라벨 예시**를 요청에 넣기 | 질문 해석 호출에 예시 뱅크에서 고른 3~5개를 붙인다 |
| 우리 말투·형식 | 지시문 + 구조화 출력 | 이미 적용 (문단 수·길이·존댓말·JSON 형식) |
| 우리 지식 | RAG | 이미 적용 (법제처 실시간) |
| 같은 실수를 반복하지 않게 | 실패 사례를 평가셋에 넣고 지시문·규칙을 고친 뒤 회귀 확인 | `evals/`, 단위 테스트의 문구 규칙. 이번 보이스피싱·대여금 수정이 이 방식 |
| 한 번 푼 문제를 다시 풀지 않게 | 결과를 DB에 저장해 재사용 | 예시 답변 재생, `procedure_labels`(같은 낱말이면 모델을 부르지 않음) |

**동적 예시가 미세조정보다 나은 점**: 예시를 고치면 다음 요청부터 바로 반영되고, 어떤 예시 때문에 그렇게 답했는지 추적할 수 있으며, 모델을 바꿔도(Haiku → 다음 Haiku) 그대로 씁니다. **못한 점**: 예시만큼 입력 토큰이 늘어납니다(질문 해석은 Haiku라 예시 5개 ≈ 300토큰 ≈ $0.00003).

**라벨링 데이터는 그대로 자산입니다.** 나중에 미세조정이 가능한 모델(오픈 모델의 작은 분류기 등)을 쓰게 되면 지금 만드는 "질문 → 라벨" 데이터가 바로 학습 데이터가 됩니다.

## 5. 하네스 — 모델 밖에서 품질과 비용을 지키는 장치

| 장치 | 하는 일 | 이미 있는가 |
|---|---|---|
| 구조화 출력 | 모델 출력이 정해진 JSON 형식을 벗어나지 못하게 | 있음 |
| 근거 키 제한 | 출처를 이번 요청의 근거 중에서만 고르게 (형식의 enum) | 있음 |
| 인용 검증 | 원문 구절 대조 + 법제처 재조회 | 있음 (이번에 긴 법령 이름 오탐 수정) |
| 문구 거르기 | 단정 표현·근거에 없는 숫자·개인정보 패턴 제거 | 있음 |
| 비용 상한 | 호출 전 토큰을 세어 상한을 넘으면 보내지 않음 | 있음 |
| 내려가기 | 구조화 실패 → 일반 답변, 답변 실패 → 근거만 | 있음 |
| 프롬프트 캐시 | 매번 같은 지시문·라벨 목록을 싸게 다시 읽기 | **부분** — 지시문이 짧아 효과가 작았음. 예시 뱅크를 붙이면 고정 부분이 길어져 효과가 생김 |
| 배치 API | 급하지 않은 대량 작업(라벨링)을 반값에 | **없음** — 이번 라벨링은 수백 건이라 일반 호출로 충분 |
| 평가 회귀 | 고친 뒤 같은 질문 세트로 다시 재기 | 부분 — 단위 테스트는 있고, 유료 평가는 허락 때만 |

## 6. 법률 섹션 라벨링 — 이번에 바꾸는 방식

지금: 질문 해석이 라벨을 **하나만** 고르고, 맞는 것이 없으면 `none`.

바꾸는 것:
1. **복수 라벨**: 주된 라벨 하나 + 함께 걸린 라벨 최대 둘. 예: "전세사기를 당했고 보증금을 못 받음" → 주 `lease_deposit`, 함께 `fraud`.
2. **온/오프라인 구분**: 일이 벌어진 곳이 온라인(글·메신저·거래 플랫폼)인지 직접 만난 자리인지. 명예훼손·모욕·사기처럼 절차가 갈리는 분야에서 쓴다.
3. **새 라벨 제안**: 기존 라벨이 맞지 않으면 모델이 새 라벨 이름과 낱말을 제안한다. 저장은 하되 **운영자 승인 전에는 화면에 쓰지 않는다**(지금의 `procedure_labels` 승인 흐름 그대로).
4. **기존 라벨 우선**: 예시 뱅크와 저장된 라벨에서 비슷한 것을 먼저 보여 줘, 있는 라벨을 두고 새로 만들지 않게 한다.

라벨이 정하는 것은 "어느 절차 안내를 보여 줄지"와 "무엇을 검색할지"뿐입니다. 사건의 결과나 유불리는 라벨에 담지 않습니다(절대 규칙 2).

## 7. 데이터 — 무엇으로 라벨링하는가

| 출처 | 쓰는가 | 이유 |
|---|---|---|
| 로톡·법률 커뮤니티 상담 글 | **쓰지 않음** | 실제 사람의 민감한 사연(건강·범죄·가족)이고 변호사 답변에 저작권이 있다. 로톡은 AI 수집 봇을 차단한다고 표시해 두었고(robots.txt의 GPTBot 등), 약관 페이지도 수집 금지 경로다. 프로젝트 규칙(약관이 금지한 소스 크롤링 금지, 공식 출처 우선)에도 어긋난다 |
| **법제처 찾기쉬운 생활법령정보 "100문 100답"** | **씀** | 법제처가 쓴 일상어 질문이라 개인정보가 없다. robots.txt가 수집을 막지 않고, 저작권정책이 출처 표기를 조건으로 이용을 허용한다. **질문 문장과 분야만** 가져오고 답변 본문은 가져오지 않는다 |
| 우리 예시 질문·카테고리 문장 시작 | 씀 | 직접 쓴 가상 사연 |
| 실제 사용자 질문(가린 문장) | **쓰지 않음** | 분석 목적으로 받은 것이라 학습·라벨링에 쓰려면 별도 동의와 방침 변경이 필요하다 |
| 판례 사건명·판시사항 (법제처 API) | 다음 단계 후보 | 공개 자료. 다만 일상어가 아니라 법률 용어라 질문 해석 예시로는 덜 맞다 |

## 9. 한계와 확인하지 못한 것

- **미세조정 제공 여부**: 웹 검색으로 확인했고 2026년 내용의 출처는 대부분 제3자 글입니다. Anthropic·AWS 공식 문서를 직접 열어 확인하지는 못했습니다.
- **임베딩 모델 권장안**: Anthropic 문서가 Voyage AI를 안내한다는 것까지 확인했고, 어떤 모델을 권하는지는 출처마다 달라 적지 않았습니다.
- 생활법령 질문은 정부가 다듬은 문장이라 실제 사용자의 거친 문장과 다릅니다. 라벨 분포도 실제 수요와 다를 수 있습니다.
- Haiku가 붙인 라벨은 정답이 아닙니다. 사람이 일부를 확인해야 평가셋으로 쓸 수 있습니다.

### 10.3 라벨 품질 — 읽어 본 것

- 잘 붙은 예: "폭행·상해 사건 수사 절차" → `assault`/오프라인, "이혼 시 재산은" → `family`, "회사 규칙에 해고 절차가 없으면" → `dismissal`, "징계해고 후 경력증명서를 안 줌" → `dismissal` + `wage`.
- 틀렸거나 애매한 예: 경매 권리분석 질문("저당권과 임차권이 매수인에게 인수되나요")이 `lease_residence` + `money`로 붙음(경매 섹션이 없어 가까운 것을 고름). "외국인이 혼인하면 국적을 취득하나요"가 `family`.
- 규칙이 지켜진 예: "빌린 돈을 갚으려는데 채권자가 이사 감"은 갚는 쪽이라 `none`(지시문의 규칙대로).
- **정답 확인은 하지 않았습니다.** 400건 가운데 일부를 사람이 확인해야 정확도를 숫자로 말할 수 있습니다. 그래서 이 결과는 예시 뱅크에 넣지 않았습니다.

### 10.4 서비스에 넣은 것

| 바꾼 것 | 내용 | 코드 |
|---|---|---|
| 동적 예시 | 질문과 비슷한 라벨 예시를 넷까지 골라 질문 해석에 붙인다. 예시는 직접 쓴 것 96개(홈 카테고리 문장 86 + 복합 사례 10) | `lib/ai/label-bank.ts` |
| 복수 라벨 | 주된 섹션 + 함께 걸린 절차 최대 둘. 결과의 `relatedSections` → 화면 "함께 살펴볼 절차" | `lib/ai/policy.ts`, `components/result/ResultPanel.tsx` |
| 온/오프라인 | `channel` (online·offline·both). 알 수 없으면 싣지 않는다 | 같음 |
| 새 라벨 제안 | 맞는 섹션이 없으면 이름·낱말을 제안 → 문구 검사 → `procedure_labels`에 승인 대기로 저장. 제안이 있으면 별도 분류 호출을 하지 않는다 | `lib/inquiries/procedure-hint.ts`, `analyze.ts` |
| 프롬프트 캐시 | 질문 해석의 고정 지시문에 캐시를 건다 | `lib/ai/lite.ts` |

**실제 동작 확인 (Sonnet 1건)**: "팀장이 단체 대화방에 험담을 올렸고, 항의하자 해고했고, 밀린 월급도 안 줌" → 주 `workplace_harassment`, 함께 `defamation`·`wage`, 온·오프라인 `both`. 답변 3문단(근로기준법 제76조의3·제26조·제104조) 모두 인용 검증 통과.
