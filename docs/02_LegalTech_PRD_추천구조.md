# 02. Legal Tech 프로젝트에 추천하는 PRD 구조

## 왜 일반 PRD로는 부족한가

일반 SaaS PRD(문제 → 사용자 → 기능 → 지표)에 더해 Legal tech는 아래 4가지가 **기능만큼 중요한 1급 섹션**이어야 합니다.

1. **규제·컴플라이언스** — 무엇을 해도 되는지가 기능 범위를 정함 (변호사법, 개인정보, AI 규제)
2. **데이터 출처·라이선스** — 판결문/법령을 어디서, 어떤 조건으로 가져오는지
3. **AI 신뢰성 기준** — 환각 허용치, 출처 표시, 단정 금지, 평가 방법
4. **책임 경계(Disclaimer)** — 서비스가 "정보 제공"인지 "법률 자문"인지의 선

그래서 추천하는 형태는 **"Lean PRD + Legal/AI 확장 섹션"** 입니다. AI(Claude Code)가 읽고 구현할 수 있도록 각 기능에 **수용 기준(Acceptance Criteria)** 을 붙입니다.

---

## 추천 PRD 목차 (템플릿)

```
0. 문서 정보 — 버전, 작성자, 상태(Draft/Review/Approved), 변경 이력
1. 한 줄 요약 & 비전
2. 문제 정의 — 페인 포인트, 근거(데이터/경험), 왜 지금인가
3. 목표 / 비목표(Non-goals) — 하지 않을 것을 명시 (특히 "법률 자문을 하지 않는다")
4. 사용자 & 페르소나 — 주요 시나리오(Jobs-to-be-done)
5. 경쟁·대체재 분석 & 차별점
6. 제품 범위 & 로드맵 — MVP(Phase 1) / Phase 2 / Phase 3
7. 기능 요구사항 — 기능별: 설명, 사용자 스토리, 수용 기준(Given/When/Then), 우선순위(P0~P2)
8. AI 요구사항 ★
   8.1 AI가 하는 일 / 하지 않는 일
   8.2 모델·도구 구성, 근거(RAG) 정책
   8.3 출력 규칙: 출처 표시, 단정 금지 표현, 불확실성 표시
   8.4 평가(Eval) 기준과 출시 게이트
9. 데이터 요구사항 ★
   9.1 데이터 소스·라이선스·수집 방식
   9.2 비식별/개인정보 처리
   9.3 갱신 주기·품질 기준
10. 규제·법무·윤리 ★ — 쟁점, 대응 방안, 검토 필요 항목, 면책 고지
11. 비즈니스 모델 — 과금 구조, 가격, 단위경제(Unit economics)
12. UX 원칙 & 핵심 화면 흐름
13. 비기능 요구사항 — 성능, 보안, 접근성, 가용성, 로깅
14. 성공 지표(KPI) — North Star + 퍼널 지표 + AI 품질 지표
15. 리스크 & 대응
16. 오픈 이슈(Open Questions) & 결정 로그
17. 부록 — 용어집, 절차 템플릿, 참고 자료
```

★ = Legal tech 전용으로 반드시 넣을 섹션

## 섹션별 작성 가이드

| 섹션 | 잘 쓴 예 | 피해야 할 예 |
|---|---|---|
| 비목표 | "개별 사건의 승소 확률을 수치로 제공하지 않는다" | (비목표 없음) |
| 수용 기준 | "Given 임금체불 인테이크 완료, When 결과 페이지 진입, Then 유사 판례 3건 이상이 사건번호·법원·선고일과 함께 5초 내 표시" | "관련 판례를 잘 보여준다" |
| AI 출력 규칙 | "모든 사실 주장 문장은 citation 1개 이상. 없으면 '일반 정보' 라벨" | "정확하게 답변한다" |
| 데이터 | "소스 A: 공식 Open API, 일 1회 증분, 재배포 조건 ○○" | "인터넷에서 판례를 크롤링" |
| KPI | "질문 → 결과 확인 전환율 70%, 결과 페이지 '도움됨' 60%" | "사용자 만족도 향상" |

## 운영 팁

- PRD는 `docs/PRD.md`로 리포지토리에 두고 **CLAUDE.md에서 링크** → Claude Code가 항상 참조
- 결정이 바뀌면 PRD 본문을 고치고 `16. 결정 로그`에 날짜·이유 기록
- 기능 섹션의 ID(예: `F-ARC-01`)를 커밋 메시지·테스트 이름에 사용 → 요구사항 추적성 확보
- 버전별로 "이번 버전에서 PRD 중 어디까지 구현했는가"를 체크박스로 관리

실제 작성본은 `03_PRD_햄찌법원.md`를 보세요.
